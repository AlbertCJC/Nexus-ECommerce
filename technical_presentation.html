🎤 Speaker Notes — Slide 1: Architecture & Infrastructure

Design Decisions & Trade-offs

  • Supabase-as-Backend: Eliminated custom Node/Go API layer. Trade-off: vendor lock-in to PostgREST semantics, but gained auth, realtime, storage, and edge functions with zero ops overhead. O(1) infra complexity.
  • Dual Context Pattern: AuthContext owns server-derived state (user, session, profile); AppContext owns ephemeral guest state (cart in localStorage, toasts, auth modal). Separation prevents auth hydration race conditions. AppContext uses useDebouncedLocalStorage (300ms debounce) to avoid write storms.
  • TanStack Query as Server State Cache: 5-min staleTime means repeated navigations don't refetch. gcTime: 10min keeps cache warm for back-button UX. refetchOnWindowFocus: false prevents disruptive reloads on tab switch.
  • Edge Function Rate Limiting: Fixed-window counter in rate-limit-auth Edge Function. Fail-open design: if Edge Function is down, requests proceed (availability > strict throttling). Limits: 3 signup/15min, 5 login/15min, 2 reset/hr per email.

Complexity Analysis

  • Auth flow: O(1) — Supabase handles JWT validation in PostgREST middleware; client only stores/refreshes tokens.
  • Query invalidation: O(k) where k = number of query keys matching prefix (broadcast via queryClient.invalidateQueries).
  • Cart merge on login: O(n) RPC call with n guest items — single round-trip, atomic upsert via ON CONFLICT.

The Hiring Manager Interruption

Q1: "Your Edge Function rate limiter is fail-open. What happens if an attacker DDoSes the rate limiter itself, causing it to return 500s? Do you actually get better protection or worse?"
A: Worse — fail-open means a downed rate limiter = zero protection. Mitigation: (1) Deploy Edge Function in multiple regions (Supabase does this automatically), (2) Add client-side exponential backoff on 429/500, (3) Supabase Auth has built-in rate limits as a second line of defense (their 429 on /token endpoint). The client-side withRateLimit wrapper also handles Supabase's native 429 responses independently.
Q2: "You're using SECURITY DEFINER RPCs for create_order and cancel_order. What's the attack surface if a malicious user discovers they can call these directly via PostgREST?"
A: SECURITY DEFINER runs as the function owner (typically postgres or a service role), bypassing RLS. The protection is: (1) GRANT EXECUTE ... TO authenticated — anon key cannot call them, (2) Internal authorization checks: cancel_order verifies p_user_id owns the order OR is admin via user_profiles lookup, (3) create_order requires valid p_user_id (FK to auth.users). However, a compromised user JWT could still call these — defense-in-depth requires short JWT expiry (default 1hr) and refresh token rotation.
Q3: "Why lazy-load every route with Suspense? What's the actual bundle size savings vs. the UX cost of spinners?"
A: Code-splitting reduces initial JS from ~400KB to ~120KB (gzipped) — critical for mobile 3G. The LoadingFallback only shows on first visit to a route; subsequent visits hit browser cache. Suspense boundary at AppRoutes level means one spinner for the whole route transition, not per-component. Trade-off accepted: slightly slower perceived navigation for significantly faster TTI on cold start.
🎤 Speaker Notes — Slide 2: Database Schema & Data Modeling

Design Decisions & Trade-offs

  • Integer cents everywhere: Eliminates JS 0.1 + 0.2 = 0.30000000000000004 bugs. All math (tax 10%, shipping ₱9.99 threshold) done in SQL RPCs using integers. O(1) precision, zero rounding drift.
  • Soft delete vs hard delete: useDeleteProduct sets status = 'inactive' + cascades DELETE FROM cart_items WHERE product_id = ?. Preserves order_items FK integrity (no ON DELETE SET NULL needed). Admin UI still shows inactive products for audit. Trade-off: storage bloat over time; mitigated by partition/archive job (future).
  • Denormalized order_items: Snapshots product_name, product_image, unit_price_cents at order creation. If product later changes price/image, historical orders remain accurate. Cost: ~200 bytes/item duplication; negligible at scale.
  • Composite PK on cart_items: (user_id, product_id) enforces one row per product per cart. Enables ON CONFLICT upsert in merge_guest_cart and useAddToCart.
  • Search indexes: Three indexes: (1) gin_trgm_ops on name for ILIKE '%query%', (2) gin_trgm_ops on description, (3) to_tsvector GIN for ranked FTS. search_products RPC combines all three with CASE WHEN exact match THEN 0 ELSE 1 END + ts_rank_cd ordering.

Complexity Analysis

  • Product listing (filtered): O(log n + k) where n = products, k = page size (20). B-tree on category_id, brand_id, status + sort column index.
  • Full-text search: O(log n + k log k) — GIN index scan + rank sort of k candidates.
  • Cart merge: O(m log n) for m guest items — each upsert is index lookup; single transaction.

The Hiring Manager Interruption

Q1: "You store shipping_address as jsonb in orders. What if you need to query 'all orders shipped to Manila'? How does that perform vs. normalized columns?"
A: jsonb with GIN index: CREATE INDEX idx_orders_shipping_city ON orders USING GIN ((shipping_address ->> 'city')); enables WHERE shipping_address ->> 'city' = 'Manila' at O(log n). Trade-off: slightly larger index than normalized column, but schema flexibility for international addresses (different fields per country). If query volume grows, extract city/country to generated columns + B-tree.
Q2: "Your idempotency_key is UUID with UNIQUE constraint. What happens if a user double-clicks 'Place Order' 50ms apart — two RPC calls with different keys?"
A: The client generates ONE key per checkout session and stores it in sessionStorage (checkout_idempotency_key). Checkout.jsx:102-106 — key is generated on first render, reused on retries. Only cleared on !result.alreadyExists (success). If user refreshes page, new session = new key = new order (correct behavior). The UUID uniqueness is a safety net, not the primary deduplication mechanism.
Q3: "Why SECURITY DEFINER for search_products? It's a read-only function — what's the privilege escalation risk?"
A: Valid concern. SECURITY DEFINER is only needed for create_order/cancel_order/merge_guest_cart (write operations bypassing RLS). search_products is LANGUAGE sql STABLE — it runs with caller's privileges. The GRANT EXECUTE ... TO anon, authenticated allows public search. No escalation risk because it only reads products (already readable by anon via RLS). I should drop SECURITY DEFINER from that function — good catch.
🎤 Speaker Notes — Slide 3: State Management & Authentication Flow

Design Decisions & Trade-offs

  • Single onAuthStateChange subscription: Handles INITIAL_SESSION, SIGNED_IN, TOKEN_REFRESHED, SIGNED_OUT, USER_DELETED, PASSWORD_RECOVERY in one place. Avoids scattered useEffect listeners. The mounted flag prevents state updates after unmount.
  • Token refresh error suppression: supabase.js:18-24 wraps window.fetch to suppress 400 on /auth/v1/token — expected when refresh token expires. Lets onAuthStateChange fire SIGNED_OUT naturally.
  • Rate limiting strategy: Edge Function (rate-limit-auth) is first line; Supabase built-in is second. Client-side withRateLimit throws enriched error with retryAfter for toast UI. Fail-open protects availability.
  • Guest cart merge atomicity: merge_guest_cart RPC uses ON CONFLICT (user_id, product_id) DO UPDATE SET quantity = cart_items.quantity + EXCLUDED.quantity. Single transaction — no partial merge state. Clears localStorage only after RPC success.
  • AppContext standalone toasts: Module-level _dispatch ref allows addToast() import anywhere without context wrapper. Used by useMutations.js callbacks. Trade-off: slight impurity (side effect outside React tree); mitigated by useEffect sync on mount.

Complexity Analysis

  • Auth initialization: O(1) — single getSession() call + subscription setup.
  • Guest cart merge: O(m) for m items — single RPC round-trip, each item upsert is index lookup.
  • Profile fetch: O(1) — PK lookup on user_profiles.
  • Debounced localStorage: O(1) amortized — 300ms debounce batches rapid dispatch calls.

The Hiring Manager Interruption

Q1: "Your AuthContext sets isAdmin = user?.role === 'admin' from user_profiles. What if an admin is demoted in the database but their JWT hasn't expired? They still have isAdmin: true client-side for up to 1 hour."
A: Correct — JWT statelessness means role changes propagate on next token refresh (1hr default) or manual logout/login. Mitigations: (1) Admin mutations (useCreateProduct, etc.) have onError calling ensurePermissionError which checks for 42501/403 from RLS — server is source of truth, (2) refreshProfile can be called manually, (3) For high-security ops, shorten JWT expiry (exp claim) or use Supabase's session_timebox feature. Acceptable risk for e-commerce admin panel.
Q2: "The window.fetch monkey-patch in supabase.js suppresses 400 on token refresh. What if a real 400 occurs on a different auth endpoint (e.g., /signup)? You'd silently swallow it."
A: The patch checks url?.includes('/auth/v1/token') — only the token refresh endpoint. /signup, /token?grant_type=password, etc. are different paths. However, this is fragile: if Supabase changes URL structure, it breaks. Better: let Supabase client handle refresh errors via onAuthStateChange (which it does — fires SIGNED_OUT). The patch exists only to reduce console noise. Should be removed in favor of clean error handling.
Q3: "You use useReducer in AppContext but useState in AuthContext. Why the inconsistency?"
A: AuthContext state is derived from external source (Supabase events) — user, session, loading are set by callbacks, not user actions. useState + useCallback is simpler. AppContext has complex user-driven transitions (cart add/update/remove/clear, toast queue) — useReducer centralizes logic, enables dispatch ref for standalone addToast, and makes state transitions testable. Right tool per context.
🎤 Speaker Notes — Slide 4: The Checkout Flow

Design Decisions & Trade-offs

  • All monetary math in cents (integers): subtotal_cents, shipping_cents (₱0 if ≥₱100 else ₱9.99), tax_cents = ROUND(subtotal * 0.1), total_cents. Done in both Checkout.jsx (display) and create_order RPC (authoritative). Zero FP drift.
  • Submission lock = useRef: Not useState — avoids re-render on lock acquire/release. Purely client-side guard; server idempotency is source of truth.
  • Idempotency key in sessionStorage: Survives page refresh within tab, cleared on new tab (correct — new session = new order). uuidv4() from uuid package.
  • SELECT ... FOR UPDATE in RPC: Takes row-level lock on products for each item. Concurrent checkouts for same product queue at database level. O(m) lock acquisitions for m items; held for transaction duration (~10-50ms). Prevents lost-update oversell.
  • Guest checkout flow: User fills form → clicks Place Order → !isAuthenticated triggers auth modal + redirect storage. After login, CustomerProtectedRoute reads postLoginRedirect and navigates back. Cart merge happens on SIGNED_IN (see Slide 3).
  • Payment enum only: No Stripe/PayPal integration. cod/ewallet/bank stored for fulfillment workflow. Extensible: add payment_intent_id column + webhook handler later.

Complexity Analysis

  • Checkout submission: O(1) client-side (lock + form validation) + O(m log n) server (RPC: m items × FOR UPDATE index lookup on products).
  • Concurrent checkout contention: Worst-case O(m × t_lock) where t_lock = lock wait time. Under high contention (flash sale), serialized by DB. Consider advisory locks for cart-level queuing if needed.
  • Cart calculation: O(m) reduce over cartItems — trivial.

The Hiring Manager Interruption

Q1: "Your create_order RPC does SELECT ... FOR UPDATE on each product sequentially in a loop. If a cart has 50 items, that's 50 round-trips inside the transaction. What's the lock hold time, and can this cause deadlocks?"
A: It's a single PL/pgSQL function — no network round-trips. The loop runs inside the postgres backend; FOR UPDATE acquires locks sequentially in the same transaction. Deadlock risk: YES if two transactions lock products in different orders. Mitigation: sort cart items by product_id before looping (add ORDER BY (v_item ->> 'product_id')::UUID to jsonb_array_elements). Currently not done — this is a bug. Should fix by sorting in RPC or client.
Q2: "The idempotency key lives in sessionStorage. What if the user opens checkout in two tabs, fills both, and submits Tab A then Tab B?"
A: Each tab gets its own sessionStorage → different UUID keys → two orders created. This is intentional — separate browser tabs = separate user intents. If you want cross-tab dedup, move key to localStorage keyed by cart hash. Current behavior: Tab A succeeds, clears key; Tab B submits with its own key → new order. Correct for "user deliberately opened two tabs".
Q3: "What happens if create_order succeeds (order inserted, stock decremented) but the client crashes before receiving the response? The idempotency key is still in sessionStorage — user retries, gets alreadyExists: true. But what if they clear storage and retry?"
A: If they clear sessionStorage, new key → new RPC call. The RPC checks WHERE idempotency_key = p_idempotency_key — no match → creates duplicate order with same items (stock already decremented!). This is a hole. Fix: add unique constraint on (user_id, cart_item_hash) or compute a server-side idempotency key from user_id + items hash in RPC. Current UUID-only approach only protects against client-side retries, not storage loss.
🎤 Speaker Notes — Slide 5: Search, Filtering, & Performance Optimization

Design Decisions & Trade-offs

  • URL as source of truth: ProductFilters reads useSearchParams() on mount; all filter changes call navigate({ search: params.toString() }). Enables deep-linking, browser history, and SSR. page param auto-resets on filter change (line 54, 66, 74).
  • Debounce at component level: useDebounce(localSearch, 300) — local state updates instantly (responsive UI), URL updates only after debounce. Prevents 300+ history entries per query. onBlur and Enter force immediate sync.
  • Search delegation pattern: useProducts checks if (search && search.trim()) return useSearchProducts(...). Single hook API, two implementations. Fallback ILIKE in fallbackSearch() handles migration lag gracefully.
  • Ranked search results: search_products RPC orders by: (1) exact name match first, (2) ts_rank_cd (cover density ranking), (3) created_at DESC. Better relevance than pure ILIKE.
  • Index strategy: Three GIN indexes (~50MB each at 1M products): trigram on name, trigram on description, FTS on tsvector. B-trees on filter columns. status partial index (WHERE status = 'active') would help but not yet added.
  • Query deduplication: TanStack Query key includes JSON.stringify(filters) — different filter combos = different cache entries. staleTime: 5min means filter toggles within 5min hit cache.

Complexity Analysis

  • Filtered product list (no search): O(log n + k) — B-tree index scan on category_id/brand_id/status + sort column, limit k (20).
  • Full-text search: O(log n + k log k) — GIN index scan candidates + rank sort of k results.
  • Trigram ILIKE fallback: O(log n + k) — GIN trigram index scan, no ranking overhead.
  • Debounce overhead: O(1) per keystroke — timer management only.

The Hiring Manager Interruption

Q1: "Your search_products RPC uses websearch_to_tsquery which parses Google-style syntax (quotes, minus, OR). What if a user searches for 'iPhone 15' — does it match 'iPhone 15 Pro'?"
A: websearch_to_tsquery('english', 'iPhone 15') → 'iphone' & '15' (AND). to_tsvector on 'iPhone 15 Pro' → 'iphone' '15' 'pro'. Match: YES (both tokens present). But 'iPhone 15' won't match 'iPhone15' (no word boundary). Trigram ILIKE '%iPhone 15%' would match 'iPhone15'. The RPC combines both: ILIKE OR tsvector @@ tsquery — so partial matches still work via trigram path. Good hybrid approach.
Q2: "The ProductFilters computes brandCounts by reducing over the products prop. If I have 10,000 products and paginate (20/page), the brand counts only reflect the current page — not the full filtered set."
A: Correct — brandCounts is computed from products prop which is the current page from useProducts. This is a bug: facet counts should reflect total matches, not page. Fix: (1) Add brand_facets column to RPC return, or (2) Separate useBrandFacets(filters) query that aggregates GROUP BY brand_id on filtered set. Current UX shows misleading counts — e.g., "Sony (0)" on page 2 even if Sony has 50 products total.
Q3: "You're using JSON.stringify(filters) in query keys. What if filters contains a Date object or Set? Keys become inconsistent, cache misses."
A: filters in this app only contains primitives: search (string), categoryId (uuid string), brandIds (string[]), sortBy (enum string), limit/offset (numbers). No Dates/Sets/Objects with non-deterministic key order. However, brandIds array order matters — ['a','b'] ≠ ['b','a'] in JSON. Fix: sort brandIds before stringify: brandIds: [...filters.brandIds].sort(). Currently not done — could cause duplicate cache entries.
